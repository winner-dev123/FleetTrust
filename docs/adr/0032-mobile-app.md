# ADR-0032: Mobile app on Expo dev builds and Expo Router, with device ports, web-path deep links, offline drafts and an idempotent message outbox

- Status: Accepted
- Date: 2026-11-24

## Context

Prompt 25 builds the iOS and Android app (SRS F-093). It covers:

- authentication;
- nearby provider search and maps;
- service requests;
- community and messaging;
- push notifications;
- trusted-contact emergency flows;
- the location permission and offline drafts.

The acceptance criteria ask for device-level permission tests, deep links, notification behaviour and degraded network scenarios, all documented.

Constraints already in place:

- **Firebase hybrid** (ADR-0004): Firebase Auth, FCM and App Check on the client. `@react-native-firebase` needs native modules, so the app uses Expo dev builds, not Expo Go (OQ-20 default).
- **Shared code:** one API through `@fleettrust/sdk`, which validates every response; tokens in `@fleettrust/ui`.
- **Push addressing:** the API addresses pushes to Firebase Installation IDs (ADR-0024).
- **Idempotency:** creating a service request, raising an alert and sending a message are all idempotent through a client-generated ID (ADR-0021, ADR-0025, ADR-0024).
- **Map vendor:** not chosen (OQ-13).

## Decision

1. **Expo SDK 58 dev builds, Expo Router, React Native Firebase 27.**
   - Screens are files in `apps/mobile/app/`. Logic lives in `apps/mobile/src/`.
   - Native projects are generated by `expo prebuild` (continuous native generation) and are not committed.
   - `app.config.ts` holds the permissions, plugins and link domains.
   - Firebase config files come from EAS file secrets at build time and are never committed.
2. **Device ports.**
   - Every native capability sits behind a small interface in `src/platform/types.ts`: auth, push, location, storage, network and device.
   - `native.ts` implements them with:
     - React Native Firebase (auth, installations, messaging, App Check);
     - `expo-location`;
     - `react-native-permissions`, for the notification prompt (React Native Firebase has deprecated its own);
     - AsyncStorage;
     - NetInfo.
   - Screens never import a native module (a guard test enforces it). Tests install a fake device, so every flow runs in Jest.
3. **Deep links use the web's paths.**
   - The app opens three kinds of URL:
     - its own scheme, `fleettrust://…`;
     - universal links / verified Android app links on the web origin and the Firebase Hosting link domain;
     - Firebase email sign-in links.
   - Every incoming URL passes through `+native-intent.tsx` → `resolveIncomingUrl`:
     - web paths are mapped to app screens (`/app/requests/<id>` → `/requests/<id>`);
     - IDs must match a strict pattern;
     - unknown paths and foreign hosts open the home screen.
   - Push messages use the same mapping (`notificationPath` in `@fleettrust/types`, shared with the web inbox). Records the app has no screen for open the notifications list.
4. **Sign-in: email link only, for now.**
   - Firebase emails a link to `<web>/auth/finish` with `handleCodeInApp`, the iOS bundle ID and the Android package, so the phone opens it in the app.
   - The address is kept on the device for up to a day, so the same phone doesn't ask for it again.
   - Sign-in links are accepted only from trusted hosts.
   - Google and Apple sign-in are left out: on iOS, Google requires Apple too (KC-01), and both need native SDK setup. They come together later.
5. **Push.**
   - **No prompt at launch:** the app asks for notification permission only when someone turns notifications on (Account), or at a moment where they help (after sending a request, on the trusted-contacts screen).
   - **Registration:**
     - When allowed, the Firebase Installation ID is registered after every sign-in (`PUT /v1/me/devices`).
     - It is unregistered before sign-out, so the next person on the phone doesn't get the previous person's notifications.
   - **Delivery:**
     - Taps from quit and background open the record.
     - In the foreground, a banner offers "Open" and "Dismiss".
6. **Offline behaviour depends on how safe a retry is.**

   | What               | Offline behaviour                                                                                                                 | Why                                                                                                    |
   | ------------------ | --------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
   | Chat message       | Queued in an outbox on the phone and sent automatically when online; a refusal is shown as "Not sent" with Retry and Delete       | The API dedupes by `clientMessageId`, so resending can't duplicate                                     |
   | Service request    | Saved as a draft as you type; **Send is disabled offline**; a failed send can be retried and reuses the draft's `clientRequestId` | A request is a commitment and uses plan quota; it shouldn't leave the phone without the person knowing |
   | Comment            | Saved as a draft; posting needs a connection                                                                                      | No idempotency key for comments                                                                        |
   | Emergency alert    | **Never queued.** Disabled offline, with "call your local emergency number"; a retry reuses the same `clientIncidentId`           | A silently delayed alert could mislead someone who needs help now (ADR-0010)                           |
   | Emergency guidance | Bundled in the app; shows offline, signed out, and when the API is down                                                           | It must always be available                                                                            |
   - **Storage:** drafts and the outbox live in AsyncStorage, per user. They expire after 7 days, are validated on load, and are erased at sign-out. No tokens are stored by the app (Firebase keeps its own session).

7. **Realtime chat.**
   - A small client for `/v1/realtime`:
     - the token goes in the first frame, never in the URL;
     - it keeps the highest `seq` per conversation, so after each reconnect it subscribes with `after` and duplicates are dropped by seq.
   - **Reconnecting:** backs off from 1 to 30 seconds, pauses while offline or in the background, and stops for good on 4403 (suspended).
   - This is the realtime path ADR-0031 left to mobile; the web keeps polling.
8. **Location: foreground only.**
   - "While using the app" is asked only when someone taps "Use my location". Background location is blocked in the config on both platforms (guard test).
   - Every screen that uses location also accepts a typed place.
   - "Blocked" (the OS won't ask again) leads to Settings.
   - Approximate positions (iOS approximate location) are labelled as such.
9. **Map:** the web's built-in XYZ tile map, now shared from `@fleettrust/ui` (`map.ts`). Pins are numbered buttons; move and zoom buttons are the alternative to dragging. No map SDK until OQ-13.
10. **Shared helpers moved out of the web app:**
    - map maths → `@fleettrust/ui`;
    - date, price and distance formatting → `@fleettrust/types`;
    - notification links → `@fleettrust/types`;
    - `errorMessage` / `isOffline` → `@fleettrust/sdk`.

    Their tests moved with them.

11. **Tests.**
    - **Logic (Jest):** deep links, drafts, outbox, realtime, push registration, sign-in and permission wording.
    - **Screens:** run through `expo-router/testing-library`, which renders the real route files, root layout included, at a given URL on the fake device. The fake API validates every response through the real SDK.
    - **Guards:**
      - copy rules (same as the web);
      - no native imports in screens;
      - no background location;
      - link domains only for https hosts.
    - **Real devices:** device checks need a dev build and a Firebase project, so they are a written plan (`docs/qa/mobile-device-test-plan.md`), not CI.

## Consequences

- **Firebase project needed:** a dev build needs the owner's Firebase project files and Apple and Google developer accounts (OQ-19). Until then the JS bundle is built and tested in CI, but no device build is made.
- **Link files on the web origin:** universal links need `apple-app-site-association` (Apple Team ID) and `assetlinks.json` (Play signing certificate fingerprint) on the web origin and the link domain. They're listed as owner items and can be served by the web app once the values exist.
- **The outbox is per phone:** a message queued on one phone isn't visible on another until it's sent.
- **Not in the app yet:** businesses, fleets, plans and appeals stay on the web; the Account screen links there. Photo uploads, groups, friends, vehicles and jobs aren't in the app yet.

## Alternatives considered

- **Firebase JS SDK instead of React Native Firebase:** it works in Expo Go, but has no FCM or App Check attestation on native, and installations need IndexedDB.
- **expo-notifications for permissions:** it installs its own FCM service and notification delegate, which conflict with React Native Firebase messaging. `react-native-permissions` only asks.
- **react-native-maps:** needs a Google Maps key on Android and picks a vendor before OQ-13.
- **Queueing alerts and requests offline like messages:** rejected for the safety and quota reasons above.
- **React Navigation configured by hand:** Expo Router gives file routes, typed links, `+native-intent` and a test renderer that exercises real deep links.
